MemPalace Integration — Code Review

Brain-Agent (cctest) · review of the MemPalace integration on main

Reviewed: b6e39ff4 · Method: three parallel read-only audits (agent tools & security gate · writer daemons & persistence · admin surface / tests / config), every CRITICAL/HIGH finding re-verified directly in the source.

Verdict

The integration's query-side security model is strong — wing isolation is multi-layered and fails closed, and the GDPR dispatch symmetry for mempalace tools is correct. The problems are concentrated on the write side (lock discipline, cursor bookkeeping, silent write loss) and the admin surface (two cross-tenant authz leaks, one inert config endpoint).

CRITICAL

CriticalC1 — /v1/mempalace/drawers admin gate bypass via trailing slash

server.py:1545 (path = self.path.split("?")[0], no rstrip("/")) → _auth_gate (server.py:1436-1460) checks exact membership in _ADMIN_GET_EXACT/_ADMIN_GET_PATHS (server.py:1292, 1317). Dispatch uses path.startswith("/v1/mempalace/drawers") (server.py:1822).

GET /v1/mempalace/drawers/?wing=user__<victim> (trailing slash) passes _require_auth() for a non-admin, and _handle_mempalace_drawers (handlers/admin_observability.py:1853-1915) has no authz of its own — it dumps the first 300 chars of every drawer (plus closets) in any wing, including project__*.

Fix: normalize path.rstrip("/") before gate+dispatch (covers all endpoints), or add _require_role("admin") inside the handler.

HIGH

HighH1 — Remote reranker egresses RAW drawer text before the GDPR seam

engine/mempalace_glue.py:704-740 · config.json:2812-2820

Rerank runs on raw_results before _gdpr_anon_tool_text (mempalace_glue.py:1137). _RemoteReranker.predict POSTs {query, documents} — up to 40 passages × 1500 chars of raw project PII — to http://192.168.1.214:8002 (prod config: reranker.enabled=true, device="remote"). Not covered by the web-egress gate, args-deanon, or the result seam. PII leaves the machine in anonymising sessions.

Fix: in anonymising sessions (_gdpr_mapping_id set), skip remote rerank or run it on the anonymised result.

HighH2 — save_chat_to_memory immediate sync advances the cursor past unwritten messages

server.py:4631-4696 (_do_sync)

Each tool_add_drawer is wrapped in try/except Exception: pass (server.py:4685), failures are not tracked, and mempalace_update_cursor(session_id, max_id) runs unconditionally (server.py:4691). A lock-refused write (mine in progress) is swallowed and the turn is permanently absent from memory — the retired chat-sync daemon had a clamp for this (server_daemons.py:1002-1006), the live replacement doesn't. This is the exact v9.60.4 data-loss class, now unrecoverable.

Fix: take _palace_write_lock around the write; clamp the cursor to min(max_id, lowest_failed - 1).

HighH3 — POST /v1/mempalace/kg/config writes to the wrong file — KG settings save is inert

handlers/admin_observability.py:807-808

os.path.dirname(os.path.abspath(__file__)) + "/config.json" resolves to the checked-in handlers/config.json 17-line stub, while every reader (_load_mempalace_config, the GET handler, the daemons) uses the repo-root config.json. The changelog even acknowledges this (brain.py:536, v9.113.0) and it was never fixed. UI shows old values on reload; the cursor-invalidation block reads an empty palace_path → no purge.

Fix: double-dirname (as sibling handlers do at admin_observability.py:321, 357, 391) and delete the stub.

HighH4 — /v1/mempalace/session-turns has no session-ownership check

server.py:1820 · handlers/admin_observability.py:251-302

Startswith dispatch, not in any admin list; the handler never calls _session_access_check. A non-admin can probe any session_id and learn which turns are memorized — a cross-user metadata leak.

Fix: gate via self._session_access_check(sid) (owner/team/admin), matching every other session endpoint.

MEDIUM

MediumM1 — _palace_write_lock does NOT serialize "ALL MemPalace writes" as documented

CLAUDE.md:251 · server_lib/db.py:91, 138, 289 · server.py:3329-3345, 4680 · server_daemons.py:515-521

Bypassing writers: _purge_mempalace_session/_purge_mempalace_turns → col.delete (also an O(corpus) unfiltered col.get per session deletion), _memorize_mempalace_turns, the profile mirror purge+add, and sched-artifact writes. All fail closed silently — a refused write just disappears.

Fix: hold the lock around every purge/add cycle; surface refusals instead of swallowing them.

MediumM2 — _purge_drawers_by_room_and_source can livelock

server.py:3259-3311

Line 3294-3295 counts success:False as deleted. With ≥200 drawers and persistent refusals (e.g. a long project-sync mine) the while True re-lists 200 and re-deletes 200 forever — a hot livelock in the caller thread (miner startup-purge, user-profile daemon, profile-doc endpoint).

Fix: count only real successes; add a no-progress iteration bail; wrap in _palace_write_lock so refusals become waits.

MediumM3 — tool_mempalace_kg_search uses an unescaped, case-insensitive LIKE — cross-project triple leak

engine/mempalace_glue.py:1762-1763, 1782, 1800

LIKE '<prefix>%' without escaping _/% and without COLLATE BINARY: /my_project/ matches triples from /myXproject/; case collides too. The extraction side already solved this (_anchored_prefix_sql, engine/kg_extract.py:254-265) but the agent-facing tool doesn't use it; the other two KG tools use exact startswith — this path is the inconsistent (leaky) one.

Fix: reuse _anchored_prefix_sql semantics (exact = prefix OR escaped-prefix LIKE) with COLLATE BINARY / instr(source_file, prefix) = 1.

MediumM4 — GDPR seams fail OPEN on internal errors

brain.py:4248-4254 · brain.py:4024-4028

_gdpr_anon_tool_text returns raw text if the pseudonymiser sweeps throw (comment: avoid "silently hiding content") — for retrieval sources this is exactly the fail-closed boundary the retrieval dialog builds. _gdpr_retrieval_guard swallows its own scan errors and falls back to apply-only, so fresh PII passes raw. A transient pseudonymizer crash silently ships raw project PII to the chat LLM in an anonymising session.

Fix: for sources in _RETRIEVAL_PII_SOURCES, return the refusal envelope (or audit a fail-open event) instead of raw text.

MediumM5 — _rebuild_via_sqlite_swap races the write daemons

engine/mempalace_glue.py:138-200

The recovery swaps the live palace via two os.renames while daemons may concurrently upsert (daemons hold _palace_write_lock, this path does not). A write landing between the renames goes into the renamed-aside directory — new drawers silently missing from the "live" palace until a full re-mine. The verification step can't detect it.

Fix: perform the swap under _palace_write_lock; verify the aside dir's newest writes are served after swap.

MediumM6 — Partial-write "skipped forever" in project-sync

server_daemons.py:1806-1836 + miner chunk batches (1000/drawer-batch)

process_file deletes a file's old drawers, then writes chunks in sub-batches stamped with source_mtime per chunk. A mid-file failure (e.g. broken extraction model) leaves partial drawers carrying the current mtime; every subsequent cycle's mtime pre-filter skips the file — a re-mine can end up permanently truncated.

Fix: stamp source_mtime only after all sub-batches succeed (or verify stored chunk count matches).

MediumM7 — No tool-result size cap on the agent-facing path

engine/mempalace_glue.py:995-1092, 1062, 1709, 1823-1832, 1897-1905 · engine/tool_exec.py:615-620

Up to 25 drawers with unbounded text, 200 triples + 300 edges → ~100KB+ single calls into the LLM context. _apply_tool_result_budget is "currently NOT called on the interactive chat path". Cost and context-bloat vector.

Fix: cap the serialized payload (truncate text/span/triple/edge counts past ~30KB) and/or wire the budget middleware into the interactive path.

MediumM8 — chat-sync daemon is RETIRED but docs + admin surface still present it as live

server_daemons.py:637-646 · server.py:4571-4573 · docs: CLAUDE.md:298-301, INVARIANTS.md:247-265, README.md:46

The loop prints and returns; server.py no longer launches it. GET/POST /v1/mempalace/classifier edits 4 keys (model, enabled, categories_to_file, min_turns) with no live consumer (only default_mode is read, handlers/chat.py:7321). Dead machinery still documented as running.

Fix: delete the dead body + shrink the classifier surface to default_mode, or update the docs (skill 05-internals.md already has the correct text).

MediumM9 — Zero test coverage of the write side and authz

tests/ — grep for _palace_write_lock, session-turns, mempalace/stats, mempalace/drawers, cursor/daemon names: zero hits

Nothing pins: write-side wing isolation, cursor clamp/retry, lock discipline across writers, admin-surface authz (the C1/H4 leaks were never pinned), KG endpoint per-user isolation. Existing tests (14 wing-isolation + 5 reranker) are query-side only.

MediumM10 — Config drift in the mempalace block

config.example.json:2746-2836 vs readers engine/kg_extract.py:860, engine/mempalace_glue.py:1277-1278

Code reads keys absent from config.example.json: kg.parallel_workers, reranker.remote_timeout_s, reranker.api_key. kg.batch_size: 20 ships with no reader anywhere. The "currently on chroma backend" note is stale (Qdrant).

LowL1 — Cross-project count oracle

engine/mempalace_glue.py:1708 (total_before_scope_filter) · :1142 (total_before_filter)

Content is filtered correctly, but the counts reveal how many matching triples/drawers exist in other tenants' wings for the same entity — a metadata oracle.

LowL2 — Helpdesk mode exempts the explicit-wing pre-check

engine/mempalace_glue.py:399

In helpdesk mode a prompt-injected Brainy can target a foreign wing; the unconditional post-filter still drops rows (fail-closed today), but it is a wing-presence oracle and an ordering hazard if the branch is ever moved before the post-filter.

LowL3 — tool_wiki_read passes limit but the query tool only reads n_results

What looks solid

  • Query-side wing isolation is genuinely multi-layered and fails closed — _wing_visible (mempalace_glue.py:286-315) default-denies malformed tenant prefixes; explicit-wing pre-check (:399-405) + unconditional post-filter (:546-551); project force-scope refuses on missing id (:385). Pinned by 14 tests.
  • GDPR dispatch symmetry for mempalace tools is correct — args-deanon whitelist membership (GDPR_ARGS_DEANON_TOOLS), every result through _gdpr_anon_tool_text with retrieval-guard sourcing, dialog fail-closed paths (background/scheduler/timeout/cancel return kinds-only refusals). Pinned by test_gdpr_retrieval_dialog.py, test_dispatch_symmetry.py, test_project_pii_curation.py.
  • Lock design is right where applied — the RLock composes correctly with the package's per-thread-reentrant file flock, no deadlock path found; miner and project-sync hold it on all main mine/delete paths.
  • Crash-safety of the retired daemon cursor logic — drawer writes commit before the cursor advances; a crash between just re-processes and hits dedup. The clamp (server_daemons.py:1002-1006) is well-designed dead code worth resurrecting.
  • Per-project error isolation + fingerprint convergence in project-sync — sync_log run row closed on every path; no skip-loops.
  • 4-site tool wiring complete for all five memory tools; HNSW corruption rebuild cooldown-gated and globally serialised; KG tool hygiene (kg.close() in finally, capped BFS/spans).

Suggested fix order

  1. C1 + H4 — authz (one-line-ish each, cross-tenant read).
  2. H1 — reranker egress gate (PII off-machine).
  3. H2 + M1 — lock + cursor clamp on the live immediate-sync path (silent data loss).
  4. H3 — KG config write target.
  5. Then M3/M4 (retrieval leaks, fail-open), M5/M6 (races), docs cleanup (M8, L5, L6).
