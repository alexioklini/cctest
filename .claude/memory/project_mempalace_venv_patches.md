Brain imports MemPalace **directly** from `~/.mempalace/venv/lib/python3.14/site-packages/mempalace/` (NOT the repo, NOT MCP). That venv is the server's actual site-packages (server runs `/opt/homebrew/bin/python3` but `config.json → mempalace.venv_site_packages` puts this venv on path). It's gitignored, so local patches are **invisible to git and survive nothing** — every `pip install --upgrade mempalace` overwrites them. Re-apply by hand after each upgrade.

**Patch (4): `closet_llm.py` — HARD wall-clock deadline on the LLM HTTP call.** ADDED 2026-06-18. SYMPTOM: the project-sync closet-regen thread wedged 30+ min in `sock_recv` (resp.read()), gumming up the whole MemPalace daemon (KG done, but run stuck 'running'; generic miner also lock-blocked behind it). ROOT CAUSE: `urlopen(req, timeout=HTTP_TIMEOUT_S=60)` only bounds IDLE GAPS between socket ops; CLIProxyAPI trickles SSE/keepalive bytes that reset the per-op timer every few seconds, so a stalled upstream makes `resp.read()` block forever. FIX (all `# BRAIN-PATCH`): `import threading`; new `HTTP_TOTAL_DEADLINE_S=90`; wrap the urlopen+read so a `threading.Timer` force-`resp.close()`s after the total deadline → the blocked read raises immediately → the existing 3-retry loop / return-None path runs. Belt-and-suspenders with the per-op timeout. (KG's own LLM path goes via sidecar background_call with timeout_s=1800 — finite ceiling, lower risk, NOT patched.) NOTE: same class as [[project_pdf_subprocess_timeout_fix]] — a blocking call with no ENFORCED total deadline wedges a thread Python can't kill; recovery from the wedge needed a restart.

**Patch (2c): `embedding.py` — MLX model PROCESS-SINGLETON (kills repeated "Loading … on MLX" reloads).** ADDED 2026-06-18. SYMPTOM: in the long-running Brain daemon the embedding model reloaded ~180× ("Loading mlx-community/embeddinggemma-300m-bf16 on MLX (Metal)…" + an HF metadata GET each time), spread minutes apart across mining/warmup ops — making project mining slow (each reload ~1.5s). ROOT CAUSE not fully pinned: `get_embedding_function()`'s own `_EF_CACHE` works in isolation (verified: same instance, model stays loaded), but in the daemon it MISSES repeatedly → a fresh `EmbeddinggemmaMLX` gets built → `_lazy_load()` re-ran the heavy `load()`. FIX (upgrade-safe, defends regardless of why the upstream cache misses): module-level `_MLX_MODEL_CACHE: dict` keyed by repo; `_lazy_load()` reuses an already-loaded `(model, tok)` if present, only calls `mlx_embeddings.utils.load()` on a true first-load per repo. So even with N fresh EF instances, the MLX load happens AT MOST ONCE per process. Verified: 2 fresh `EmbeddinggemmaMLX` instances → ONE "Loading…" line, `ef1._model is ef2._model` True, embed still 384-dim L2-normed. TWO `# BRAIN-PATCH` edits in `EmbeddinggemmaMLX`: the module-level `_MLX_MODEL_CACHE` + the cache check inside `_lazy_load()`. (Composes with 2b's set_cache_limit/clear_cache — those stay.) NOTE: did NOT chase the upstream `_EF_CACHE`-miss root cause; if it's ever found, this patch is still a cheap safety net.

**Patch (2b): `embedding.py` — MLX Metal buffer-cache release.** ADDED 2026-06-08. The `EmbeddinggemmaMLX` backend was holding **24 GB resident `IOAccelerator (graphics)`** in the Brain daemon (PID had 25 GB phys_footprint via `footprint`, but `ps` RSS showed only 62 MB — GPU/wired memory is invisible to RSS). Root cause: MLX keeps a **process-wide Metal buffer-cache pool** that grows to the high-watermark of every batch and never shrinks; the model itself is only ~600 MB. TWO `# BRAIN-PATCH` edits in `EmbeddinggemmaMLX`: (1) `_lazy_load()` after `load()` → `mx.set_cache_limit(512*1024*1024)` (cap the reuse pool at 512 MB; beyond that returns to OS); (2) `__call__` wraps the embed body in `try/…/finally: mx.clear_cache()` — `np.array()` already forces `mx.eval` materialization so the result is host-side before the clear. Verified: after a 2-text batch `cache=0.1MB active=615MB peak=655MB`, vectors still 384-dim L2-normed (norm=1.0000) → idle footprint drops 24 GB → ~600 MB, output unchanged. APIs confirmed present in mlx 0.31.2 (`mx.set_cache_limit`/`mx.clear_cache`/`mx.get_cache_memory`); both guarded in `try/except` so older mlx no-ops. Negligible perf cost (clear_cache just frees pool; unified memory re-allocs cheaply).

### ⚠️ CoreML EP is NaN-broken on this Mac (HARD GOTCHA, 2026-06-06)
embeddinggemma via the DEFAULT `embedding_device: "auto"` picks **CoreMLExecutionProvider**, which produces **100% NaN embeddings** here (CoreML splits the quantized ONNX graph: "279 of 1647 nodes supported"). MUST force a non-CoreML device. Options that work: `embedding_device: "cpu"` (ONNX-CPU, slow but correct) or `"mlx"` (our patch, fast). NEVER leave embeddinggemma on `auto`/`coreml` on this box — silent NaN corruption of every vector. Caught only because we tested vectors before the re-mine.

## Upgrade procedure (verified 3.3.5→3.4.0, 2026-06-06)
1. `pip download mempalace==<v> --no-deps --no-binary :all:`, untar, diff `knowledge_graph.py` + `backends/chroma.py` + `embedding.py` vs the clean copy to re-derive patch line locations (3.4.0 moved lots).
2. Back up palace first: `cp -c brain/chroma.sqlite3 ...pre<v>-bak` + KG sqlite (CoW).
3. Stop server GRACEFULLY: `launchctl bootout gui/$(id -u)/com.brain-agent.server` (bootout, NOT just SIGTERM — it's KeepAlive so SIGTERM alone gets restarted; bootout unloads). Wait for process gone + no open handles on chroma.sqlite3. NEVER SIGKILL ([[feedback_never_sigkill_brain]]).
4. `~/.mempalace/venv/bin/python3 -m pip install --upgrade mempalace==<v>`.
5. Re-apply the 2 active patches (span + MLX). Re-install `mlx mlx-embeddings` if the venv was rebuilt.
6. Verify: round-trip a span triple; `get_embedding_function()` returns clean non-NaN 384-dim vectors (CHECK FOR NaN — the CoreML gotcha); brain.py compiles; bootstrap server (`launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.brain-agent.server.plist`); confirm `/v1/status` version + log shows `Embedding function initialized (... device=mlx)`.

To find ALL current patches: diff every `.py` in the venv mempalace against a clean download.
