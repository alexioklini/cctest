Evaluating **Microsoft FastContext** (github.com/microsoft/fastcontext) — a Qwen3-4B-Instruct-based **read-only repo-exploration subagent**: takes NL query, drives its own Read/Glob/Grep loop, returns `file:line` citations in a `<final_answer>` block. It is **NOT** a code editor and **NOT** a CodeGraph replacement (CodeGraph = deterministic tree-sitter/SQLite exact lookup; FastContext = an LLM that greps). Real fit = a project-scoped **delegation** subagent for code-mode that saves main-agent context tokens. User wanted: serve MLX-quant on M4, and TEST replacing the 7B bg model (will fail — it's a tool-caller, not a general chat model).

**Models published**: `usermma/FastContext-1.0-4B-RL-mlx-8Bit` (4.3GB, qwen3, 8bit affine g64, 262K ctx) — best, used as primary. `rubybear/FastContext-1.0-4B-SFT-mlx-4bit-g32` (2.4GB) = RAM-saver. ⚠️ 4-bit HURTS the core job: card File-F1 8bit=0.507 vs 4bit-g32=0.300 vs 4bit-g64=0.050 (citation line numbers corrupt under quant). Use 8-bit. Base = Qwen/Qwen3-4B-Instruct-2507. License MIT (clears bank-deploy, unlike marker/OpenRAIL).

**Serving recipe that WORKS** (M4 = DGX-Mac, 192.168.1.214, 24GB):
- vllm-metal (`~/.venv-vllm-metal/bin/vllm`), NOT `mlx_lm.server` (the latter has slow prefill + no KV cache → 47K-token turn took ~5min).
- `vllm serve usermma/FastContext-1.0-4B-RL-mlx-8Bit --port 8016 --served-model-name fastcontext-rl-8bit --kv-cache-dtype turboquant_4bit_nc --enable-auto-tool-choice --tool-call-parser hermes --max-model-len 64000`
- **PARSER = `hermes`, NOT `qwen3_xml`**. The model emits `<tool_call>{json}</tool_call>` (Hermes JSON). With qwen3_xml vllm doesn't parse tool calls → loop returns raw `<tool_call>` text → no exploration. hermes = same parser the 7B uses.
- **Co-serving FastContext-8bit + 7B caps FastContext ctx at ~64-80K** (100K OOMs: needs 13.7GiB KV, only 11.35 free with 7B resident; vllm est max ~82K). Standalone it could do more.
- Harness: `pip install -e` from `git clone microsoft/fastcontext` (NOT pypi `fastcontext` — that's an unrelated 2022 bio pkg). Needs ripgrep (`rg`); M4 has no brew → static arm64 binary in `~/bin/rg`. Env: FC_BASE_URL/FC_MODEL/FC_API_KEY/FC_TEMPERATURE/FC_MAX_TURNS. `work_dir = os.getcwd()` (run inside the repo checkout). Repo synced to `~/cctest-eval` (rsync, exact HEAD).
- **Harness bug**: `--citation` crashes (`format_citations` iterates the dict that `parse_citations` returns on the no-`<final_answer>` path → TypeError). Run WITHOUT `--citation`, parse `<final_answer>` yourself. Eval harness at `eval/fastcontext_eval.py` + gold `eval/fastcontext_gold.json` (15 verified query→file:line, this repo).

**First eval (max-model-len 40K, max-turns 6)**: 5/15 file+line hit. BUT confound: **when it answered, 5/5 were line-precise** (q01 model_select:298, q04 server_daemons:62, q12 quotas:526, q13 brain.py:7225, q15 brain.py:8223). The 10 MISSes were EMPTY (no answer), caused by **context overflow** — brain.py is 1.7MB with a giant inline CHANGELOG; grep hits it, FastContext reads huge ranges, context blows past 40K → 9× HTTP 400 → loop yields nothing. So the score measured "FastContext vs a pathologically large file", not model capability. Re-running the 10 empties at 64K ctx / 8 turns to separate config-too-tight from model-can't.

**FINAL VERDICT (after ignore re-test)**: distractor exclusion (`.ignore` with docs/research/ + packaging/ + *.app/ — rg-respected by both Grep+Glob tools, neither passes --no-ignore) **cleanly removed all distractor hits** but score did NOT recover: ignore-run 6/15 file, 5/15 line. Removing the docs/research+dist distractors just shifted the model to NEW wrong files (q03→handlers/chat.py, q06→claude_cli.py, q11→server_lib/db.py) — it was never really finding the brain.py-resident golds, the distractors were a symptom not the cause. ROOT KILLER = **brain.py monolith** (1.7MB, ~22k lines, giant inline CHANGELOG): 5 of 6 hard misses are brain.py-resident; FastContext's read-large-ranges strategy can't navigate it (overflow at 40K, 500-680s thrash at 64K). Best-case across all 3 runs = 10/15 file, 8/15 line. **Latency: median 109s, 5/15 over 300s, max 683s** — far too slow for an interactive pre-edit retrieval subagent vs CodeGraph (deterministic, instant) or the main agent just grepping. By difficulty: exact 3/5, concept 0/4 (worst — needs semantic understanding), misplaced 3/6. **DECISION: do NOT integrate.** Not worth it on this repo until brain.py is split (which is independently desirable but a big job). CodeGraph + main-agent-grep already cover the niche faster. Model weights + harness + 3 result JSONs left on M4 (~/cctest-eval/eval/) + locally (eval/fastcontext_*.{py,json}) for re-test if brain.py ever gets decomposed.

GOTCHAS: never SIGKILL ([[feedback_never_sigkill_brain]] is about brain-agent, but M4 7B is separate — 7B was launched by sparkdash (`~/sparkdash.py` :8013, instance registry `~/sparkdash-instances.json`) but runs detached under launchd pid 1, NOT actively supervised, so killing it won't auto-respawn).
