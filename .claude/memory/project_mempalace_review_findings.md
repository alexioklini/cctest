2026-06-02: Adversarial multi-agent review of the MemPalace integration (engine/mempalace_glue.py, server_daemons.py 3 daemons, server_lib/mempalace_sync.py, kg_extract.py). Findings VERIFIED against real code. **ALL 8 FIXED in v9.60.4** (see brain.py CHANGELOG; wing-isolation regression tests added). Summary of what each fix did is below — kept as a record of the failure modes to guard against in future MemPalace work.

**CRITICAL — cross-tenant data leak via explicit `wing` arg.** `tool_mempalace_query` applies the `_wing_visible` C3 gate ONLY on the `_needs_user_filter` path, which requires `not wing` (glue ~296, filter ~414). When the LLM passes an explicit `wing` (e.g. `user__bob`, `project__<other>`, `team__<foreign>`) AND no project is active, NO visibility check runs → Chroma returns the foreign wing's drawers verbatim. `wing` IS LLM-exposed in the tool schema (engine/tool_schemas.py ~472) and its desc even falsely claims "auto-scoped to the current user". Reachable by a misaligned/prompt-injected model. ALSO fails OPEN when `current_user_id` is empty (anonymous/background): `_needs_user_filter`=False → `{}` where-filter → searches every wing. FIX: make `_wing_visible` an UNCONDITIONAL post-retrieval choke point on the non-project/non-helpdesk path (drop the `if _needs_user_filter` guard) + pre-check refusing a foreign explicit wing. SOLID by contrast: project force-scope (glue 268-281) overwrites caller wing with `project__<safe_pid>`, refuses on missing id — a project chat can't be widened. KG tools scope-check + refuse outside project — safe.

**HIGH — silent permanent write loss in chat-sync (two agents found this independently, same root).** chat-sync advances the cursor to `max(new_last_id, max_msg_id)` (server_daemons.py ~900) REGARDLESS of whether tail drawers filed. `_file_drawer` returns False on (a) a swallowed `add_drawer` exception and (b) `res.success==False` — which is exactly what the package's NON-BLOCKING `mine_palace_lock` returns (`MineAlreadyRunning`) when another daemon holds it. So under normal daemon overlap (miner/project-sync mid-mine while chat-sync upserts), the write is refused, returns False, but the cursor jumps past it → message permanently skipped from memory. Same bug for the summary cursor (~901, advances `summary_hash` even if summary drawer write failed). FIX: advance cursor only to the highest id whose write succeeded-or-confirmed-dedup; treat `MineAlreadyRunning`-refused writes as retryable (don't advance).

**HIGH — auto-recovery (`_try_rebuild_palace`, glue 128-152) is weak for the dominant corruption class + races writers.** (1) Calls legacy `repair.rebuild_index`, whose FIRST op is `col.count()/get()` — which itself raises for the `InternalError: Failed to apply logs to the hnsw segment` (#1308) class that the `"internal error"` marker matches, so recovery no-ops on the most common shape; needs `repair.rebuild_from_sqlite` fallback (reads sqlite directly). (2) Rebuild does delete-collection→recreate→bulk-upsert with NO write quiesce — can re-trigger the bulk-delete-races-upsert corruption it's recovering from, and drop embeddings_queue rows not yet flushed. (3) cooldown stamped before work → failed rebuild = 120s retrieval blackout. NOTE: the v9.60.3 sync_threshold=1000 + graceful-shutdown fix addresses the ROOT trigger (so recovery should fire rarely now), but recovery itself isn't rock-solid.

**MEDIUM — corruption markers too broad / dead.** `_MEMPALACE_HNSW_CORRUPTION_MARKERS` (glue ~113): `"hnsw"` matches benign config errors (hnsw:space mismatch), `"internal error"` matches transient SQLITE_BUSY/disk errors → spurious expensive rebuild. `"nothing found for"` is DEAD (nothing emits it) but its name invites a future maintainer to wire empty-results→rebuild (would blast every empty wing). FIX: tighten to `"error finding id"` + `"failed to apply logs to the hnsw segment"`; delete the dead marker.

**MEDIUM — no Brain-side serialization across the 3 write daemons.** The package `mine_palace_lock` is per-palace NON-BLOCKING; Brain's miner/chat-sync/project-sync don't coordinate → losers get `MineAlreadyRunning` (feeds the HIGH write-loss above). `srv._project_sync_lock` does NOT protect palace writes (only in-memory request bookkeeping — server.py ~599). FIX: one in-process `srv._palace_write_lock` held around each mine()/add_drawer batch/stale-purge delete.

**MEDIUM — stale-purge `col.delete(ids=...)` (server_daemons ~1511-1544) not serialized vs upserts** = the documented [[project_chroma_bulk_delete_corruption]] trigger, unguarded. Same fix (palace write lock). Also: `kg_purge_for_scope` (~1286) + `_count_wing_drawers_by_source` (~1290) use UNANCHORED prefix match (`proj1` matches `proj1extra`) → cross-scope DELETE / inflated counts. `_is_stale_src` itself IS anchored (trailing os.sep) — safe.

**MEDIUM — project-sync: one project's unhandled raise aborts the WHOLE cycle** (server_daemons ~1389, body not per-project try/except) → every later project starved for the 6h interval. FIX: wrap each project body in try/except+continue.

**MEDIUM — KG source-invalidation ordering (kg_extract ~900-923).** Records new source-state cursor BEFORE re-extraction completes + deletes triples and progress in two separate commits → crash window leaves a changed file with ZERO triples permanently (progress says done, triples gone). FIX: record source-state only after re-extract; delete progress before/atomically-with triples.

VERIFIED CLEAN (no fix): reranker cache load (lock-correct), config cache (benign last-writer-wins), contextvars in query path (daemons don't touch it), KG per-instance connections (single writer + WAL), `_mempalace_last_rebuild` locking.
