**v9.210.0** (2026-06-26): CodeGraph (`engine/code_graph.py`) made **per-tenant**. Was ONE global DB (`agents/main/code-graph.db`) everyone wrote to (miner→brain-source for Brainy, agent `code_graph_build`, `_after_file_write` hook) with NO project scoping/leak-guard — a code-mode project building its graph would clobber Brainy's, and vice-versa. Origin: FastContext eval ([[project_fastcontext_eval]], rejected) → user realized the real fix was scoping CodeGraph like MemPalace.

**Decisions (user-locked, don't re-litigate):** EXACTLY 2 tenants — (a) brain-source for Brainy (stays `agents/main/code-graph.db`, miner-built, unchanged), (b) one graph per **code-mode** project at `agents/<id>/projects/<name>/code-graph.db`. NOT extended to attachments/outputs/ingest (ground truth: project-ingest REJECTS source code — parser map is docs-only; attachments/outputs are 1-2 files where a graph buys nothing). Gated to the 2 tenants — NOT available in normal chats/non-code projects. DB under project dir (not in working_dir).

**Mechanism (the non-obvious parts):**
- Scoping key = `RequestContext.code_graph_db` (new field, engine/context.py). Set in `brain.apply_domain_context` code-mode branch (alongside working_dir) to `<_pcfg["dir"]>/code-graph.db`. None → global. Carried through tool-call rebuild (build_tool_context + sidecar_proxy background dict + tool_mcp `_apply_context` + allowed-keys list) like working_dir.
- `_code_graph_conn()` now resolves path from ctx per-call + is **path-keyed** (dict `_code_graph_db_pool.conns[path]`, was single `.conn` slot) so a pooled thread switching project↔normal never reuses the wrong handle. Schema inits lazily per new path. `CodeGraph.__init__` no longer eager-binds the global DB.
- **Gating = matrix `deferred` + code-mode `undefer`, NOT exclude_tools.** config.json `tool_settings.code_graph_*`: interactive→`deferred` (normal chat doesn't pay them in-prompt, still tool_search-recoverable), helpdesk→`active` (code_graph_query only, Brainy). apply_domain_context promotes them via `ctx.undefer_tools` in code-mode. WHY undefer not exclude: exclude_tools would break the warm KV prefix (warmup keeps code_graph since it skips apply_domain_context, real normal turn drops it → divergence = the v9.9.10 drift class). deferred is seen by BOTH warmup + first turn → identical prefix. (Plan agent caught this — exclude_tools was my first wrong instinct.)
- GOTCHA fixed: handlers/chat.py classifier-driven `undefer_tools` write ASSIGNED (`_ctx.undefer_tools = _undefer`) → clobbered the code-mode undefer. Changed to UNION.
- Leak-guard: `_unbuilt_project_graph_error()` in code_graph.py — code_graph_query/impact return "run code_graph_build first" if code-mode + project DB has 0 code_nodes (path already scoped so can't read brain-source; guard just prevents empty-looks-like-not-found).
- Miner (server_daemons.py): UNCHANGED — daemon thread = empty context → resolves to global DB = its tenant. Only commented.

**Verified live (v9.210.0, server healthy):** in-process against the real `qb` code-mode project (working_dir /Users/alexander/Documents/dev/qb): apply_domain_context → code_graph_db=agents/main/projects/qb/code-graph.db, all 4 tools undeferred; normal chat → None/global, no undefer. Built qb graph (7 files, 122 nodes/518 edges) → project DB created, **global DB mtime UNCHANGED** (isolation proven), leak-guard fired on unbuilt project. No path-bleed across requests on same thread. NOT a curated changelog entry (backend/architecture, no new UI control — matches v9.206.0 precedent).
