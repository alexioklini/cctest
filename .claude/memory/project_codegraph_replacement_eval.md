Started 2026-06-27. Goal: pick the most capable source-code indexing for PRODUCTION code-mode projects (cctest-scale: ~159k LOC, 235 code files, 14k-line brain.py — current toy projects like wettervorhersage are NOT representative). Target consumer = a LOCAL 7B or Mistral model that must work efficiently against a repo too big to hold in context, so structural+token-efficient retrieval is the prize.

**Candidate:** codebase-memory-mcp (github.com/DeusData/codebase-memory-mcp, MIT, v0.8.1, 16k★). Single static C binary; tree-sitter 158 langs + "Hybrid LSP" type resolution (9 core langs) + openCypher (read-only) + FTS5/BM25 + simhash + git-poll watcher. Runs as MCP stdio server OR per-command CLI (`cbm cli <tool> '<json>'`). Store: SQLite per project under `~/.cache/codebase-memory-mcp` (`CBM_CACHE_DIR` overrides). To integrate MemPalace-style (NOT MCP) = shell out to CLI per tool call, wire 4-site into TOOL_DISPATCH/GROUPS/DEFINITIONS + per-purpose matrix + undefer in code mode + code_graph_db-style tenant routing via CBM_CACHE_DIR.

**KEY FINDING (decides the architecture):** its embedder is `nomic-embed-code` (768d int8) COMPILED INTO THE BINARY. NO swap, NO external-endpoint config, and the EMBEDDING/INFERENCE SOURCE IS NOT IN THE REPO (src/ has graph/AST/cypher/store/watcher; src/semantic = ast_profile only; no tensor/weights/ggml). So: (a) the MemPalace MLX venv-patch trick is STRUCTURALLY IMPOSSIBLE here; (b) "patch the C to use MLX" = fork+rebuild a closed inference path AND would downgrade code search (nomic is code-specialized; embeddinggemma is general) → rejected; (c) you cannot feed it external vectors — its semantic search is 1 of 11 FUSED signals inside its own store, not a redirectable vector lookup.

**Three arms vs cctest:**
1. CURRENT = in-tree engine/code_graph.py (name-based edges, 14 langs). Build cost 0.
2. A-PARALLEL = codebase-memory-mcp as-is (structure + its OWN nomic-CPU semantic search); MemPalace/MLX stays for prose/docs. Two embedding systems, agent routes. Build cost LOW (install+index+CLI).
3. A-UNIFIED = codebase-memory-mcp for STRUCTURE ONLY + code-semantic-search done in OUR MLX→Qdrant (one embedding stack on Metal). NOTE: cannot turn its embedder OFF (compiled in) — just don't call it. Requires BUILDING a new code→Qdrant indexer+tool. Build cost HIGH. Uses embeddinggemma (general) on code, likely slightly worse than nomic but unified + Metal.

**DECISION (user, 2026-06-27): STAGED + repeatable harness.**
- Phase 1 (cheap, FIRST): Current vs A-parallel. Index cctest in both, run fixed gold question battery. Answers "is the C engine worth adopting at all?" + "how good is nomic-CPU on cctest code?"
- Phase 2 (ONLY if Phase 1 justifies): build MLX→Qdrant code indexer, test A-unified's semantic half vs A-parallel's. Don't build the expensive arm until evidence warrants.
- Harness = eval/codegraph_arena.py + gold question set with ground truth derived from cctest (callers_of/impact/imports structural Qs + fuzzy "find code that does X" semantic Qs). Metrics: structural accuracy, semantic top-k recall, TOKEN cost of answer payload (the small-model viability lever), index time, per-query latency, + end-to-end task completion by a local 7B with each engine's retrieval.

IMPLICATIONS for the decision:
